一、说清楚：省下来的是敲命令的时间

有人问，这跟敲命令有啥区别。如果你够厉害，够有经验，那自然是你准备好的脚本更棒了。

但对于经验未必很丰富的新手朋友来说，恐怕区别挺大的。你自己配一台新机器，要处理的东西散在十几个地方：apt 源要不要换、pip 走哪个源、npm registry 怎么设、conda 装哪个版本、CUDA 驱动有没有对上、HuggingFace 拉不动怎么办。每一件单看都不难，可你得先知道有这回事，才想得到去处理。如果是新手，可能遇到很多坑，都不知道怎么回事，也未必知道如何找到解决方案，然后再四处搜索，焦头烂额。

智能体的价值在于它可以帮你解决掉这些坑，而且愿意一条一条列出来供你选择，然后你确认只要把要求说清楚，剩下就是等。

二、先说硬件和 BIOS 设置

作为针对单独硬件平台开发的框架，Halogen 只认 AMD Ryzen AI Max+ 395，代号 Strix Halo，核显 Radeon 8060S，ROCm 那边叫 gfx1151。这颗芯片有点特别：16 核 Zen 5 加 40 CU 的 RDNA 3.5 核显，再挂一个 NPU，128 GB LPDDR5X-8000 直接焊在板上，CPU 和核显共用这一块，带宽 256 GB/s 上下。容量有128G以上，所以能装下一百来 GB 的量化权重，靠的就是这份统一内存。

我朋友这台正好是这个配置。顺手拿它当例子。

机器到了，在装系统之前，先进 BIOS 改一样东西。

UMA Frame Buffer Size，中文界面有的叫"显存划分"，调到最小，最低只给 4 GB。别留在 Auto，Auto 是让固件自己挑，挑大了那块内存就白扯了。

为什么这条重要。Strix Halo 的内存不是分区的，而可以简单看作是映射：BIOS 里这个 carve-out 只是给核显划一块保底的，真正给 AI 用的是内核里的 GTT，把系统内存动态映射进 GPU 的地址空间。AMD 自己的 ROCm 文档写得很直接，建议把 BIOS 里的专用显存留小，比如 4 GB，再靠调大共享的 TTM/GTT 上限来补。carve-out 留大了，那块内存就归核显专用，系统看不见，模型也用不满；留小了，GTT 才有的可映射，128 GB 里能用的可以留给内存到 124 GB，显存只给 4 GB。

网上有些教程让你在 BIOS 里直接划 96 GB 当显存，那样也能跑，只是这块内存从此要不回来，完全放模型权重又不够大，内存剩余也不够大，这样机器想同时干点别的就难受了。

我倾向小 carve-out 加 GTT，就是内存设置为 124GB，显存设置为 4GB，这样对 Halogen 来说是最优的。

硬件和 BIOS 这两件事都对上了，剩下的才可以往下走，去装系统、去配环境、去跑模型。

要是你手上不是这颗芯片，halogen 就别尝试了。其他家的核显、12 GB 的独显、甚至 4090 48GB 等等，那些机器想跑本地模型，Strata 更合适。

三、第零步：装系统，建议 Ubuntu

装系统这事我不展开，各家情况不一样，按你习惯来。只说一个建议： 如果这台机器后面要跑 CUDA 或者 ROCm、要跑本地模型、要跑各种推理框架的话，装 Ubuntu 26.04.1 LTS，可能是最方便的。

有人说 Windows 不是更省事？省事是省事。可 ROCm 那一整套东西都是先在 Linux 上测出来的效果最好， NVIDIA 的驱动也是，类似的还有 CUDA Toolkit、TensorRT、vLLM、SGLang、llama.cpp， 等等，官方文档给的第一选项基本都是 Ubuntu，或者有些项目干脆不给 Windows 的说明。

硬件方面可能也是类似，Linux的硬件支持目前最丰富也最全面，拿 DGX Spark 为例，是 GB10 Grace Blackwell，20 核 Arm，ARM64 架构，128 GB LPDDR5x 统一内存，出厂的 DGX OS 基于 Ubuntu 24.04。英伟达把自家参考机器放在 Ubuntu 上，这事本身就说明问题，要是 Ubuntu 上的 CUDA 一堆毛病，他们不会这么干，对不？

但当然了，DGX Spark 是 ARM64，你手上那台大概率不是。今天绝大多数个人电脑都是 AMD64 架构。这个名字听着像 AMD 专属，其实是 x86-64 的另一个叫法，Intel 处理器跑的也是它，只是名字从 AMD 那边来的。你机器上 uname -m 打出 x86_64，那就是 AMD64；打出 aarch64，那是 ARM64。DGX Spark 属于后者。

所以装 Ubuntu 的理由有两条， 一是框架生态都对 Ubuntu 的支持一直很好，甚至往往优先都是 Ubuntu。二是 Ubuntu 不用担心 Windows 的正版授权问题。

四、第一步：先弄一个不用自己掏 API key 的智能体

这是整套流程的前提，也是很多人卡住的地方。

智能体助手这两年出了一大堆。绝大多数要你自己准备 API key 或者绑卡，环境都还没配好，先要解决计费，这对新手来说就像是卡bug了，如果玩不转，后面可就弄不出来了。

本文掩饰的这两个都不用额外准备 key，注册完直接用。

4.1 opencode：node 走 apt，别用 nvm 那个脚本

要在命令行里干活的东西，我还是习惯 opencode。它原生是个终端程序，配置文件就是纯文本，想改哪改哪，不用去找菜单。

Ubuntu 自己的源里就有 node 和 npm，直接装：

sudo apt update
sudo apt install -y nodejs npm
node -v      # v22.22.1
npm -v       # 9.2.0

Ubuntu 26.04 给的是 node 22.22.1 加 npm 9.2.0。版本够不够新呢？其实足够了，实际上，opencode 的 npm 包里没写引擎要求，18 以上都能跑。

这会儿 apt 源还是默认的，装这两个包不至于等太久，等装完智能体，下一步配镜像会让它把源全换掉，那时候就快了。

顺手把全局包的目录挪到自己家，后面 npm install -g 就不用 sudo：

mkdir -p ~/.npm-global
npm config set prefix ~/.npm-global
echo 'export PATH=$HOME/.npm-global/bin:$PATH' >> ~/.bashrc
source ~/.bashrc

然后换源装：

npm config set registry https://registry.npmmirror.com
npm install -g @opencode/cli
opencode --version

我这边查 npm view @opencode/cli version 拿到的 latest 是 2.0.32。实装了一遍，npm install -g @opencode/cli 几十秒装完，opencode --version 回的是 opencode v2.0.32。

装完你会有 opencode 和 opencode2 两个命令，指向同一个二进制。机器上如果早就装着 v1 的 opencode，用 opencode2 起 v2，两个能并着放，不至于互相顶掉。

有人担心 npm 装完还要去 GitHub 拉二进制，那换源就白换了。@opencode/cli 解开只有 3 KB、四个文件：一个 package.json，一个 LICENSE，一个空的可执行文件，一个 postinstall。真正的二进制在 @opencode/cli-linux-x64 这类 optionalDependencies 里，由 npm 自己下。我把那个 postinstall 从头翻到尾，里面没有任何网络请求，只干一件事，把 node_modules 里的二进制拷出来。所以整个安装过程都在 npm registry 上，换到 npmmirror 之后全程走镜像，一个 GitHub 地址都不碰。

还有个坑。全局包装完提示 command not found，是 bin 目录没进 PATH。npm config get prefix 看一下，把它下面的 bin 加进 ~/.bashrc，然后关闭当前终端，新开一个终端看看激活新的环境变量试试。

4.2 WorkBuddy：不碰命令行的话

有些朋友不想跟终端较劲，只想有个图形界面，最好还能从手机或者微信远程指挥家里那台机器。这类需求就应该是腾讯出的 WorkBuddy 合适，从 CodeBuddy 那条线做过来的。

官网的下载页只挂着 Windows 和 Mac，Linux 的走这个地址：

https://www.workbuddy.cn/v2/update?platform=workbuddy-linux-x64-deb

这里有个细节得先说清楚：这个地址返回的不是安装包，是一段 JSON。我实测拉下来是这样：

{"version":"5.6.2.40046327","url":"https://download.codebuddy.cn/workbuddy/saas/linux-x64-deb/WorkBuddy-linux-x64-deb-5.6.2.40046327-c7b525f3.deb","sha256hash":"12149ad8c0cd748fd5062d8f62c7827d688d8095427ada99b1ae9e7019897523"}

所以最省事的做法是浏览器直接点这个链接，它会把安装包下下来。想在命令行里装就取 url 字段：

curl -s 'https://www.workbuddy.cn/v2/update?platform=workbuddy-linux-x64-deb' \
  | jq -r .url | xargs wget
sudo dpkg -i WorkBuddy-linux-x64-deb-*.deb
sudo apt install -f -y     # 依赖不全的时候补一下

装完注册登录就有免费额度，目前不充钱也能有一定额度使用，还有一些免费模型，反正趁早用吧。

4.3 怎么选

要改配置文件、要把它接进脚本、要接到本地模型上，建议选 opencode。要图形界面、要手机远程指挥，选 WorkBuddy。当然了，这两个不冲突，我的台机器上往往是两个都装着。

五、第二步：让智能体先把镜像配好

这一步最要紧。

原因很简单。后面所有的下载都卡在网络上，apt 慢，pip 超时，npm 卡住，conda 装一半断掉，HuggingFace 连不上。镜像不改好，后面每一步都在重试，智能体再能干也得耗在这儿。

所以顺序是：先配源，再干别的。

具体换哪些，常见的是这几个，我刚拿 curl 挨个探过，当前都返回 200：

用途 镜像地址
apt https://mirrors.ustc.edu.cn/ubuntu/
pip https://mirrors.ustc.edu.cn/pypi/simple/
conda https://mirrors.ustc.edu.cn/anaconda/
npm https://registry.npmmirror.com/
HuggingFace https://hf-mirror.com/

全部用中科大 USTC，就是上面这五个地址。

可以不自己写这些命令，直接派给智能体。下面这段你可以原样抄：

先帮我把这台机器的国内镜像全部配好，配完再动别的。需要覆盖这几处：apt 源（换中科大 USTC）、pip（换中科大 USTC，写进 ~/.pip/pip.conf，不要只 export 一个环境变量）、npm（registry 换 registry.npmmirror.com）、conda（换中科大 USTC 的 anaconda 源）、HuggingFace（设 HF_ENDPOINT=https://hf-mirror.com 并写进 ~/.bashrc）。改之前先备份原来的配置文件。改完每一条都实际验证一次，比如 pip 装个小包、npm view 一个包、把 apt update 花了多少秒打出来。哪一条没验证通过就告诉我原因。

这段话里有三个地方是实践出来的：

首先是无论任何操作，永远先进行备份，别直接覆盖你现有的配置。

写进配置文件，别只在当前 shell 里 export。一个 export 你换个终端就失效，后面跑下载脚本时又用不上镜像了。

要求验证。"改完了"这三个字不算数，得看到 pip install 真的成功、apt update 的结果也能显示出来。

六、第三步：要本地模型，先从魔搭把权重拉下来

ModelScope（魔搭）是国内的大模型托管平台，上面的权重基本是从 HuggingFace 同步过来的官方镜像，国内直接下。

Halogen 是 Peonist（peonist.ai）做的推理引擎，它在魔搭上有组织页：

https://www.modelscope.cn/organization/peonist-ai

这个组织下面挂着五个模型，主模型、embedding、reranker 都有。我查了 HuggingFace 上对应的名字：

  • peonist-ai/halogen-qwen3.8-27b
  • peonist-ai/halogen-qwen3.8-flash-next
  • peonist-ai/halogen-npu-qwen3-embedding-0.6b
  • peonist-ai/halogen-npu-qwen3-reranker-0.6b

魔搭上的路径就是 https://www.modelscope.cn/models/Peonist-ai/ 加模型名。

但你压根不用管这些，你直接把他们的组织页面发给你的智能体工具，让他帮你都弄好，直接把这段发给智能体：

读一下这个页面 https://www.modelscope.cn/organization/peonist-ai ，把这个组织下所有模型都下载到本机。要求：1）统一放在 /data/models/<组织名>/<模型名>/ 这样的目录，每个模型一个文件夹，权重、config、tokenizer 这些原始文件都留着；2）在每个模型目录下写一份 README，写清楚这模型干什么用、量化档是什么、需要多少显存和内存；3）按页面上的文档把推理服务起起来，给我一个能直接 curl 的地址；4）下载要能断点续传，别让我从头再来；5）需要 root 的命令单独写成一个脚本放到 ~/Desktop，不要执行。

这段是给 halogen 用的，因为它有组织页可以整包拉。上一条里 Strata 那句原话照发就行，不用改。

每一条都有理由：

  • 指定目录结构，是因为模型文件一大就是几十上百 GB，散在各处迟早找不到。

  • 要 README，是因为三个月后你自己都不记得那个文件是干什么的。

  • 要断点续传，是因为大文件下到一半断掉是常态，不是意外。

  • 要 root 命令单独成脚本，下一节讲。

我更倾向让它把下载做成脚本，脚本里带进度和断点，然后我在终端敲一条命令让它跑。为啥不直接让它跑？一半原因在下一节。

七、root 密码绝对不要泄漏！

智能体会跟你要 sudo，要你输 root 密码。这个我建议是千万别给。

智能体的对话内容要送到模型服务去，你在对话框里敲的每一行都是内容的一部分。密码敲进去就出去了。这个风险你想想？

我的做法是让智能体把所有需要 root 的命令按条目整理成一个脚本，放到桌面，告诉路径，剩下的自己跑。派给它的话这么说：

接下来凡是需要 root 权限的命令，都不要执行，也不要让我输密码。把这些命令按执行顺序整理成一个脚本写到我桌面，每条命令上面加一行注释，说明它在做什么、为什么需要 root。脚本第一行加上 set -e，方便我看出错在哪。写完把脚本路径告诉我，我自己跑。

它交回来大概是这么个东西：

#!/usr/bin/env bash
set -e

# 换 apt 源到中科大 USTC,要往 /etc/apt/sources.list.d/ 写东西,所以要 root
sudo cp /etc/apt/sources.list.d/ubuntu.sources ~/ubuntu.sources.bak
sudo tee /etc/apt/sources.list.d/ubuntu.sources > /dev/null <<'EOF'
Types: deb
URIs: https://mirrors.ustc.edu.cn/ubuntu/
Suites: resolute resolute-updates resolute-security
Components: main restricted universe multiverse
Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
EOF

# 编译工具链,后面装 Python 包会用到
sudo apt update
sudo apt install -y build-essential git curl wget

# 推理服务用容器跑
sudo apt install -y docker.io
sudo systemctl enable --now docker

我拿到之后先读一遍。看清楚了再敲：

less ~/Desktop/setup-root.sh
bash ~/Desktop/setup-root.sh

sudo 在这里要密码，输的是我自己的，终端本地读，不外传。

这个做法还有个附带好处：脚本留在那儿了。机器以后出问题，或者三个月后重装，这个脚本本身就是一份完整的安装记录，不用重新回忆当时装了啥。

八、几个要留意的

智能体说它做完了，你自己得看。这是最要紧的一条。它跑完一轮，要么让它贴命令和输出，要么自己去验证。看输出比看它的总结靠谱。

Docker 装完可能得重新登录。newgrp docker 或者重登一次，不然还是 permission denied。

大模型权重体积很大，一份量化权重 100 GB 上下很常见，一定确保空间足够，装之前先 df -h 看一眼之类的。

魔搭的组织页是网页，不是 API。智能体去读的时候会自己想办法，如果他用的模型太笨了搞不定了，那你最好把模型列表也直接贴给它，省得它猜。

这套流程是智能体给你一个方案，你得能够自己判断和决定，每一步都要知道自己在干什么。

给的目录结构合不合理、量化档选得对不对、端口有没有冲突，这些它给不了。

九、什么情况下别这么干

不是所有场景都适合派活。有几种情况别用：

你本来就熟、十分钟能搞定的活，派它反而更慢。

机器上有别人在用的东西、别人配好的环境，别让它乱动，这种环境让它改风险太大。

你对结果有严格要求又验不了的环境，先别急着上。

生产服务器更不用，它给的任何一行都别照搬。

十、其实并不难，能动手试试就行

整条流程是五步。装 Ubuntu，自己想办法。装一个不用自己掏 API key 的智能体，opencode 或者 WorkBuddy 都行。让它把 apt、pip、npm、conda、HuggingFace 的镜像全换掉，每一条都验证过。要本地模型，先看机器是不是那颗 Strix Halo、BIOS 里的 UMA carve-out 有没有调小，对上了再把魔搭的链接丢给它，让它按规范下载、排好目录、写好文档、把服务起起来。需要 root 的命令让它写成脚本放桌面，自己读一遍自己跑。

前两步大概十来分钟。后面的全是慢慢让智能体自己弄了。

我自己用智能体弄完这一套花的时间，比当初自己摸索着配要少得多。之前配环境前后弄了好几周，后来有了智能体，都省事多了。

但是，大家还是得了解基本原理，就是当建筑师可以不是熟练的施工工人，但是具体流程都得明白。

现在看上去好像是模型降低了开发门槛，什么外行人用模型似乎都能做出点东西来，但实际上对于内行来说提高效率的增益远胜过外行人的瞎折腾。

孩子们一定要成为内行人，避免陷入「一切交给模型」的盲目状态中。

否则你遇到坑了自己也未必能弄明白，模型其实就更未必靠谱了。
