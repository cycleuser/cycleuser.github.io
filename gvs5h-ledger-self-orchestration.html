不训练也不换模型，GVS5H通过编排让 Qwen3.8-27B 的分数从 66.8 涨到 92.4

发布于 Mon 26 October 2026 | 24 分钟 | 标签 GVS5H LiveCodeBench 多智能体 推理时扩展 Qwen3.8 模型评测

GitHub 上有个仓库叫 GVS5H，副标题是 Gorilla vs. 5 Humans，题图里 5 个人踩着肩头立成一摞，跟旁边一只大猩猩比身高。它要解决的问题说起来不复杂：同一道编程题，让模型一次把答案写完是一条路；让模型改当策划者，先拆任务、再派活、记账、验收，这又是一条路，两条路跑出来的分数最后能差出 25.6 分。作者栏填的是多伦多的 Persis Capital，署名一共 7 个人，论文明确写着没有接受资助，代码以 MIT 协议开源，论文与跑测数据以 CC BY 4.0 授权。最后一次提交在 9 月 23 日，前后共 55 次提交，整个仓库 495 MB。

一、脚手架：5 个文件，一个策划者，几个执行者

方法全称叫「基于账本的零样本自编排」（ledger-based zero-shot self-orchestration）。这里头零样本是说既没有做训练，也没有事先示范一遍该怎么拆题；账本，是说策划者和执行者之间的全部协作都走磁盘上那几个文件，不靠一条越拖越长、最后把模型自己绕进去的对话。整套实现只有 codebase/v2-current/escalation/multiagent.py 一个文件，496 行。

表 1 每道题开一个工作目录，里面放着 5 个文件

文件 装什么
task.md 题面原文
plan.md 策划者写的总策略，写进去截到 4,000 字符
tasks.json 任务清单的镜像，方便人看
notes.md 笔记，截到 8,000 字符
solution.py 当前这版答案

还有一个 answer.md，按代码里的写法，执行者交出完整程序的时候应该往里写，可我在 runs/ 里找到的 4,200 份全是 0 字节，论文正文里也没提过它。

除了验收那一步，策划者和执行者都只是同一个模型在干净上下文里的一次调用，温度各管各的：写计划 0.3，头脑风暴 0.4，做任务和整理清单 0.2，单次调用的基线也走 0.2。执行者之间互相不通气，一个执行者能看到的东西只有账本，外加策划者分给它的这一个任务。一轮的走法是这样：

  1. 策划者读题，写 3 到 6 句策略，外加 3 到 6 个起手任务；
  2. 第一个执行者被明确禁止写代码，只负责找核心难点，列出几条真正不一样的思路和各自的难处，写进 notes.md；
  3. 策划者把计划和头脑风暴合成一张任务清单，合并重复的，标上 done，只把确实新的任务加进去，然后判 done 或者点出下一个任务；
  4. 换一个执行者来做这个任务，重写 solution.py 和 notes.md，笔记是整份重写而不是追加，这轮写漏了的东西下一轮就找不回来；
  5. 这轮执行者动了代码，就拿题面自带的公开样例真跑一遍，把判定结果和第一个失败用例回给策划者当事实依据，跑不过不许判 done，必须改成「修这个失败用例」或者「换个思路」；
  6. 收尾。轮数用完、策划者把刚派出去的任务原样再派一次、或者干脆不点任务，都会再花一次调用去出终版答案；策划者判了 done 而且磁盘上有可用代码，这次调用就省掉。

约束没有几条：策划者派一次单、执行者做一单算 1 轮，上限 10 轮，同一个任务重复派出就停下来；如果哪个执行者被输出上限截断，就另外花一次短调用，把它写到一半的思路压成 3 到 5 句交给策划者，不然那点思路跟着上下文一起没了。

runs/firstparty-128k-reasoning-on-5pass/ws/q38_multiagent_p1/ 下面有道构造题，笔记一共 10 条，摘 4 条进来：

- **Reverse reduction:** Forward insertions are hard because each insertion shifts later
  elements. [...] element i is the P_i-th element among positions not occupied by larger elements.
- **Fenwick tree:** Use a Fenwick tree over N slots where 1 means empty and 0 means filled.
  For an all-ones array, the internal tree value at index i is lowbit(i), so initialize with
  bit[i] = i & -i in O(N).
- **K-th empty query:** Use binary lifting. Set top to the largest power of two not exceeding
  N, idx = 0, and iterate step = top, top/2, ..., 1. [...]
- **Sample checks:** Sample 1 traces to 4 2 3 1. Sample 2 traces to 1 2 3 4 5.

倒序归约怎么想、树怎么建、样例怎么手推，全在这几行里，一句闲话都没有，下一个执行者读到的就是这几行字，而不是前面几万 token 的思考原文。「账本」这个名字起得很贴切，不写想的过程，只写定下来的结论，结论落在纸上，下一位接着往下走。

基线跟它的差别就只有这套脚手架：同一份解题提示词，一次调用出代码。另外还有点要说清楚，100 道题里只有 73 道带按行输入的公开样例、能被上面第 5 步跑到，剩下 27 道是 LeetCode 那一类函数调用型题目，脚手架拿不到外部反馈，只能由隐藏测试打分。

六、LiveCodeBench 打分器上的 2 个不足

这一节跟方法本身没关系，却是我看得最重的一处。两处毛病都是作者查调用记录的时候发现的，都写进了附录，作者还把所有存下来的输出重新打了一遍分。

第一处在评测的执行环节。打分器不把候选代码当子进程跑，而是在同一个进程里执行，把 sys.stdin 换成一个假对象，这个假对象的二进制视图把 readline() 写成 inputs.split(b"\n")[0]，一个无状态表达式，每调一次都返回第一行。凡是用 sys.stdin.buffer.readline() 逐行读多行输入的程序，都会把第一行读 N 遍，写得再对也过不去。文本模式的 sys.stdin.readline 是正经迭代器，buffer.read() 返回全部内容，最常见的 sys.stdin.buffer.read().split() 写法碰不到它，所以一直没被发现。作者把那个视图换成 BytesIO 支撑的实现，读一次位置就前进一次，然后重打。

影响在各模型之间很不均匀，不是一个常数偏移能说完的。固定在指定后端的 5,425 份带代码输出里，371 份用了这个写法，其中 86% 被误判，没这样写的误判率 18%。Fable 5 一次都没用，分数一分没动；GPT-5.6-Terra 带策划者那一组被抬了 12.6 分。走 OpenRouter 的那批更极端，4,764 份带代码的输出里只碰过一次，还是绕了个弯用的：Kimi-K3 在 abc396_g 上把 sys.stdin.buffer 先赋给一个变量再 readline()，就是这一份，修好之后把 Kimi-K3 在 128k 开推理下的单次调用从 82 抬到 83。更要紧的是这个毛病正好跟第二版脚手架的验收步骤打架，验收把候选当真的子进程跑，那里 buffer.readline() 工作正常，于是整套脚手架唯一的外部信号，给一份隐藏测试认为错的代码盖了「公开样例通过」的章。

打分器自己先做错了一道题，这个错落在谁头上，全看谁恰好那样写。

第二处在答案键。LCB-100 里有 4 道题允许多个正确答案，abc396_e、arc190_a、arc195_c 是构造题，交出任一达到最优的构造就算对，abc385_f 要一个实数，原比赛按相对容差 1e-6 判，LiveCodeBench 的做法却是拿单个存下来的输出做字符串全等。作者按各自比赛的规则给那 3 道构造题写了校验程序，abc385_f 按容差逐 token 比较。这类缺陷上游是有记录的，勘误表里列了 11 道早期多解的题，都不在 LCB-100 里。

七、想自己实现该怎么做

README 给的命令直接能用，只需要一个 uv 和一个 API key：

cd codebase/v2-current
export OPENAI_API_KEY=...
LCB_RELEASE=release_v6 \
ESCALATION_CLOUD_MAX_TOKENS=128000 \
ESCALATION_CLOUD_TIMEOUT=7200 \
MULTIAGENT_MODEL=openai:gpt-5.6-terra \
uv run --no-project --python 3.12 --with 'datasets<4' --with numpy --with anthropic \
  python escalation/run_bench.py --engine multiagent --only lcb --lcb 100 --parallel 8

--engine multiagent 跑的是带策划者那一组，--engine single 跑单次调用做对照。MULTIAGENT_MODEL 一个 id 就把策划者和所有执行者一起定了，anthropic:、dashscope:、openrouter: 这几个前缀各认自己的 key。轮数上限由 MULTIAGENT_MAX_ITERS 管着，默认 10。分数打印在末尾，结果写 runs/results.json，每题的工作目录写 runs/ws/。

动手之前先算两笔账。表 4 那一趟只是 100 题的开销，全量 5 趟要乘 5，自己搭服务是唯一能把这笔开销压下去的路子，也正是这篇论文能够出现的原因。另一笔要算在那份 383 MB 的 runs/ 头上，里面有 9,418 份 plan.md、9,446 份 notes.md（有几个目录是符号链接，去重要少些），验收用的 solution.py 也都在；可论文「数据可用性」那段写着 runs/ 会给出带策划者那些配置的工作目录调用记录、每次调用的 finish_reason 和 token 日志，而逐次调用的记录我一份都没找到，token 只给了 per_problem_tokens.json 这一类汇总。要看策划者和执行者到底怎么对话，只能自己跑一遍，代码 496 行，按表 4 算一题几分到几毛美元。
