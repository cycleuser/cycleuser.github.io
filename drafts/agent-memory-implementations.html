智能体的记忆是怎么实现的：从滑动窗口到知识图谱

发布于 Sun 01 November 2026 | 23 分钟 | 标签 智能体 记忆 上下文 向量检索 知识图谱 MemGPT

大模型本身不记事，你每次跟它说话，它都是第一次见你。智能体那份"记得你上周说过什么"的本事，全部长在模型外面，是一堆存下来的东西加上把这些东西塞回提示词的时机。这篇文章把这些做法大概捋一遍：上下文本身、滑动窗口、摘要压缩、提示词缓存、向量数据库、结构化表格、文件树加 grep、wiki、知识图谱、分层调度、后台整理，还有那些公开跑分到底该怎么来看待。

模型本身是固定的参数

从最本质视角来看，大模型的工作方式是你递一段文字进去，它往外吐一段文字，吐完这一单就结束，他自己的参数里不留任何痕迹。下一句它还能接住你的话，是因为程序把前面所有对话重新拼成一大段，连同新的问题一起又发了一遍。你看到的"记忆"，是每次都重新发过去的那一大段。

所以一个智能体的记忆系统，说穿了只有两块：存了什么，以及在什么时刻把哪一块塞回提示词。存的地方可以是上下文窗口、文件、数据库、图，甚至也能有办法硬放进模型的权重里；塞回去的时机可以是每轮都带、检索到才带、或者干脆在没人提问的波谷时期先算好。后面所有复杂的各种花样骑士都是这两块的不同组合。

上下文窗口是模型一次能看多少内容，单位是 token，一个汉字差不多算一到两个 token，窗口大小是模型和推理引擎定的上限，装不下的部分模型就看不了。提示词是每次请求发过去的那整段文字，包括系统指令、对话历史、工具返回的结果，模型对它一视同仁，如果不标记出来，其实他都分不出哪句是你说的哪句是它自己上次说的。

先把记忆分成四类

2023 年 Princeton 那篇 CoALA（https://arxiv.org/abs/2309.02427 ）借了认知科学的老框架，把智能体的记忆切成四块，后来大部分文章和文档里的分类都从这里来。这里主要讨论的其实是"存的是哪种东西"，跟"用什么技术存"是两码事。

表 1 四类记忆对应存的内容与常见的存放载体

记忆类型 存什么 常见的存放载体
工作记忆 这一轮正在用的东西：当前任务、最近几次工具返回、手头的计划 上下文窗口本身，加上窗口里被反复引用的那几段
情景记忆 发生过什么：上一轮对话、上次运行的日志、昨天那次失败 对话记录、事件表、按时间排的向量块、轨迹文件
语义记忆 攒下来的事实：用户偏好、项目约定、查到的结论 事实表、向量库、知识图谱、markdown 记忆文件
程序性记忆 怎么做事：系统提示里的规则、技能文件、可执行的技能库 提示词与 CLAUDE.md 这类规则文件、技能库、微调进权重的习惯

按 CoALA 的说法，这四块里让模型自己去改程序性记忆是风险最高的做法。

上下文这块地怎么省着用

这是所有记忆做法的第一层，不借助任何外部存储也能跑。

最呆的做法是全塞。把整段历史原样放进上下文，不做知识库，很多人也觉得笨，但其实这样确实能用。mem0 论文里的全长上下文基线在 LoCoMo 上拿到 72.9%，可能还比不少花哨的记忆系统高。

不过呢，多轮对话加工具轨迹迟早超过任何固定窗口；输入越长越贵越慢；还有位置的问题。那篇 Lost in the Middle（https://arxiv.org/abs/2307.03172 ）测出个 U 形曲线，关键信息放在输入的开头或结尾时模型答得最好，埋在长上下文的中间就容易变差，明确做过长上下文训练的模型也是如此。

所以，可以采用滑动窗口，只保留最近 N 轮，更早的直接丢掉。实现最省事，代价是丢掉的真的没了。智能体比聊天机器人更怕这个，它一轮工具调用就能产生几千上万 token 的结果，一个长任务几十轮下来，窗口的绝大部分位置被中间过程占满，真正定方向的第一句如果被丢掉了，那岂不是大悲剧？

然后就是摘要压缩，走到窗口边上时让模型把旧内容写成一份纪要，拿纪要替掉原文。Claude Code 管这个叫压缩，DeepSeek Harness也支持这个，具体来说，可以你手动触发，也可以设一个 token 阈值到点自动触发，压缩之后会重新从磁盘读项目的规则文件，免得规则被压丢了。压缩的代价是细节没了，问它"上周三那个报错的第三行"多半问不出。摘要什么时候都该配一份，但别指望它当唯一的记忆。

另外一个思路，其实严格说不是记忆，是省钱省时间的计算复用，叫提示词缓存。模型不记事，推理那边可以把读过的 token 的中间结果留下来（工程上叫 KV 缓存，存的是每个 token 在模型里算出来的一整套中间数值），下次开头一模一样就能少算一大截。有的服务商就用明确的定价把这件事跟用户明说了：写进缓存按基础输入价的百分之一百二十五（默认 5 分钟有效），写进一小时那一档按两倍，从缓存里读按百分之十等等。Manus 那篇讲上下文工程的文章（https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus ）说大概是智能体的输入输出比平均到 100:1，所以缓存命中率比什么都要紧，命中与否差的是十倍价格。它给的规矩是提示词开头保持稳定、上下文只往后追加别改前面的字。

往提示词里塞记忆，位置既要照顾模型读得到，又要照顾缓存别被打断。开头是个好位置，稳定的规则放那儿；窗口末尾也好，刚发生的事自然在那儿。两头都不占、每次插在中间还每次换顺序，那是最糟的做法，检索没讨好，缓存也打没。

向量知识库是主流选择，但长对话未必靠谱

向量检索的做法是把文字切成块，用一个嵌入模型把每块变成一串坐标，文字意思接近的坐标也靠近。你提问时问题变成一串坐标，机器算哪几个块离得最近，把最近的几条捞回来。各种"知识库"是最常见的实现。纯按词面匹配的老办法叫关键词检索（BM25 是它最常用的实现），搜得到原话，搜不出换了说法的意思，所以现在普遍两路都开、结果合并，外面管这叫混合检索。

这条线的真实战绩得看同一套框架下的对照。AgentMemBench（https://arxiv.org/abs/2608.00009 ）把五种策略按同一个接口、同一批题库、同一个生成模型跑齐了，这是少数能横着比的表。它用的生成模型和打分模型都是 Qwen2.5-7B-Instruct 的 4-bit 量化版，n 为 491 个问题。

表 2 五种记忆策略在同一评测框架下的检索与回答指标（AgentMemBench 宏平均）

记忆策略 存储形式 Recall@5 MRR Answer F1 忠实度 每次请求带进去的 token
全文窗口（滑动窗口的学术叫法） 最近若干轮原文 0.468 0.450 0.137 0.230 297.5
外部键值加向量检索 键值记录加嵌入索引 0.792 0.677 0.156 0.354 5,126.4
图谱式情景记忆 实体关系图 0.361 0.351 0.127 0.244 5,106.2
摘要压缩 分会话摘要文本 0.556 0.461 0.137 0.252 3,478.3
加外部网络检索 窗口加网络结果 0.462 0.447 0.136 0.219 200.2

表里 Recall@5 是正确答案落进前五条的概率，MRR 看正确项排多前，忠实度衡量回答是不是只用了给它的材料，Answer F1 按字面重合算答案对不对，所以这个数天生偏低。

把 LoCoMo 单拎出来看就更有冲击力了，这个数据集的题要求翻回好几个会话之前的原话，论文里的例子是第九次对话问第一次说过想读哪本书，中间隔着大约 3,200 token。五种策略里只有带向量检索的那条拿到了 Recall@5 = 0.573，另外四条全在 0.005 以下：滑动窗口 0.000，摘要 0.005，实体图谱 0.001。作者的结论一句话能说完：时间一拉长，靠新近度的窗口、靠摘要、靠实体图谱都会塌，只有稠密检索撑得住。摘要那条能当第二，是因为它的摘要继承了自己压缩过的那些句子的出处。

图谱那条为什么这么弱呢？大概是因为他们用现成的 NER 工具从口语化对话里抽实体，抽出来的图噪声很大，如果人名没抽全，或者有什么指代关系没合并，图基本就算废了。

图 1 五种记忆策略的检索命中率与每次请求带进提示词的长度（AgentMemBench，n 为 491 题）

向量库还有两件事得提。一是写入成本很高，创建起来并不经济，另一篇做系统画像的论文（https://arxiv.org/abs/2610.34673 ）提到不少记忆系统在建库阶段一条历史就要几百到上千次模型调用。二是纯向量也不稳，词面差太远、需要精确对上型号编号或者日期的查询，光靠向量会漂，所以混合检索应该是必选的方向了。

把记忆存成文件：wiki、grep 和用时再读

这一条是近两年变化最大的一块，也是我最愿意用的，因为它便宜、看得懂、能 diff。

做法本身朴素得不像话：把记忆写成普通的 markdown 文件，不建索引、不做向量，只让模型先看见一批很短的标识，文件名、目录、一两句摘要，需要哪块再把它读进来。Anthropic 把这套叫 just-in-time retrieval，原话是只要"最小一包高信号的 token"。它的 memory 工具（https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool ）是让模型自己请求建文件、读文件、改文件、删文件，真正执行发生在调用方这边，数据落在哪儿由你自己定。Claude Code 的记忆分两摊：你手写的规则文件每次会话开始全量加载；auto memory 是模型自己记的笔记，按仓库分开维护，每次只读前 200 行或者 25 KB （https://code.claude.com/docs/en/memory.md ）。这条线上还有一批 wiki 工具：DeepWiki 把 github.com 改成 deepwiki.com 就能给一个仓库生成整站 wiki；local-deepwiki（https://github.com/derekmeegan/local-deepwiki ）更狠，wiki 由你手上那个编码智能体自己写，工具只负责用 tree-sitter 扫代码结构、用内容哈希判断哪页过期、在终端里给你翻，页面就存在 .deepwiki/ 目录里跟着仓库提交，一行外部模型调用都不加。

这些做法共同的点子是：把理解提前在写入的时候算好，而不是每次提问都现场重新推一遍。

跑分上这个方向也还不错的。LongMemEval-V2（https://arxiv.org/abs/2605.12493 ）专测智能体能不能从自己跑过的轨迹里长出经验，451 道题，历史轨迹最多 500 条、1.15 亿 token。把轨迹存成文件、让编码智能体在沙箱里自己翻的那条路平均准确率 72.5%，最强的 RAG 基线 48.5%，直接用现成编码智能体 69.3%。代价写在同一句话里：编码智能体这条路延迟很高。

知识图谱这条线跟文件那条思路还是明显不同对，它把记忆存成点和边：节点是人和项目和概念，边是带属性带时间的事实。它能答向量答不了的问题，比如穿过三个人才连上的关系，或者"到去年三月为止他管的是哪个部门"。

Zep 的引擎 Graphiti 是这条线里常被引用的实现（https://arxiv.org/abs/2501.13956 ），这里面的点是给每条事实记两个时间线：这条事实在现实里从什么时候成立到什么时候失效，以及它是什么时候被这台机器被告知的。假如用户改了主意，旧事实不是删掉，而是标成失效，于是"他现在是主管，八月之前他是组长"两件事能同时留着。论文里 DMR 上 94.8% 超过 MemGPT 的 93.4%，LongMemEval 上准确率最多提升 18.5%、响应延迟比基线降九成。那篇图谱视角的综述（https://arxiv.org/abs/2602.05665 ）中提出：图谱在显式关系、层级结构、时间性和多跳遍历上都要强过向量，但如果到了上千万节点的规模就还是有很大难题。结合上面那个 0.361，图谱在对话这种实体模糊、指代随地的数据上很容易白忙一场，值不值得上，看你具体的场景，尤其是看到底有没有关系和时间线要问。

进一步工程化其实在学操作系统的内存管理

MemGPT（https://arxiv.org/abs/2310.08560 ）的思路借的是操作系统的虚拟内存：把记忆分成三层，放在上下文里的核心记忆很小，近期对话记录可以翻回来，归档层放长期内容存在库里；关键是这三层之间由模型自己用工具搬，它能把东西写进归档、能发起检索把内容捞回窗口。后来这批研究催生了 Letta 这类框架，把记忆当成 agent 服务的状态，有的实现干脆把记忆导出成文件跟着 git 走。

有两个方向的研究者觉得"提问的时候再整理"太晚了。

一个是 sleep-time compute（https://arxiv.org/abs/2504.13171 ）：两次对话之间模型闲着，就把已有上下文先想一遍，把原始上下文加工成更好用的形态。作者造了两个改造过的推理任务来量，同样准确率下测试阶段需要的计算能省大约 5 倍；把睡眠时间的算力往上加，Stateful GSM-Symbolic 上准确率再涨最多 13%，Stateful AIME 上 18%；再拿多问题版来摊薄，单问平均成本降 2.5 倍。

另一个是生成式智能体那篇（https://arxiv.org/abs/2304.03442 ）里的 reflection：检索记忆时不只按语义相似度排，它给每条记忆打三个分再相加，新近度、重要性、相关性，三项归一化后等权。隔一段时间把最近一堆观察攒起来提一句更抽象的结论，存回库里当更高层的记忆。这个"检索分数是几项相加"的做法后来被抄得到处都是。

写入侧的成本是一定要考虑的，这是最容易被各种明星项目很多的星星数给掩盖而藏起来的。那篇系统画像论文（https://arxiv.org/abs/2606.06448 ）把九套记忆系统放进同一个框架量了一遍，用 Qwen3-32B，LongMemEval 上 300 问，建库加问答端到端的成本见下表。

整理记忆，还会带来三个麻烦，很难有标准策略应对：去重（同一件事记了三遍，检索一次多抓三条噪声）、冲突消解（新事实和旧的撞了，是覆盖还是并存，让模型自己判新旧很容易看走眼）、遗忘（直接删、随时间衰减、还是置信度低就降权）。Graphiti 那种给事实加失效时间的做法，是我目前见过最省事的冲突处理。

如果强行把东西塞进权重里，就叫参数化记忆。这样检索就根本不用外部件，代价是成本高昂：加一条要重训，删一条要搞机器删除那一套，而且可能模型自己逐渐没办法记清它是从哪条数据知道的。程序性记忆这块还有个相对稳的做法，Voyager（https://arxiv.org/abs/2305.16291 ）把学会的操作写成一段段可执行代码存成技能库，用的时候按描述去从嵌入向量找；这样存的是能跑能测能回滚的代码，比让模型随手改自己的规则文件安全得多。让模型自己改写自己的规则文件，可能会发生错误，而且就算有写错规则的情况也根本不会报错，只会让后面每一次干活的时候都偷偷跑偏。

各家定位差别挺大，选起来其实是要看你的场景：要一个能直接嵌进现有后端的 API，是 Mem0 那类；要一个长期在线、有状态、能自己维护记忆的 agent 服务，是 Letta 那类；企业里有大量带时间线的业务数据要并到一起，图谱就是可选项目；只想让编码助手少忘事，文件加规则文件最省事，成本几乎为零。

自己要用的话要先问清楚场景

先问数据能不能落在自己的本地。这条对本地部署尤其关键。

再问你的场景下，多会话长程的检索是不是核心需求。如果是，就得上语义检索；如果不是，可以干脆全文塞对话里面，简单粗暴。

接着问记忆谁来写、什么时候写。你作为架构人员自己来设计打磨规则文件自然是最可控；模型自己写的话恐怕得配上你或者一个专门智能体来审；后台再看看优化，比如能不能把数据写入延迟到低调度的时段，比如夜间空档。

然后问预算主要放在写侧还是读侧。查询量大到能摊薄建库成本，重方案才划算；查询少而短，写入路径一重就是纯亏。

第五个问题是要不要审计和回滚。纯文本文件和带失效窗口的图能 diff、能回滚；写进权重，或者放进托管服务里面什么的，可能就不好说了，就怕你连它记了什么都不知道，更别提撤销和修复了。

我建议的顺序是：先文件加 grep 加一份压缩摘要，跑一周看够不够；逐渐再补向量库或者混合检索；确实有关系和时间线要问，再上图。别一上来就上图数据库，太复杂了，也别指望换个更大的上下文窗口就把这件事解决，窗口再长也只是把撞墙的时间往后挪，中间那段它照样读不好。
