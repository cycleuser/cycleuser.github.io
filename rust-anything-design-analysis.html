rust-anything 设计思路拆解：把「用 Rust 重写」变成一条可验证的流水线

发布于 Wed 18 November 2026 | 21 分钟 | 标签 rust-anything Rust 代码迁移 智能体 MCP 性能优化 差分测试

把「用 Rust 重写」变成一条可验证的流水线

GitHub 上最近有个项目 https://github.com/erkamyaman/rust-anything，作者 Erkam Yaman，三天时间从 1.0.0 推到 1.4.0，已经 1.8k star 了。rust-anything 想解决的问题很具体：把现有的应用，一块一块地改写成 Rust，而且每一步都得证明行为稳定。支持 TypeScript/JavaScript、Python、C、Go、Ruby、Java，PHP 和 C# 在预览状态。

安装：cargo install rust-anything && rust-anything setup

rust-anything 听起来像是又一个「代码翻译器」，但读完 rust-anything 的 README、设计决策文档以及项目里给智能体写的工作流技能之后，就能确认 rust-anything 压根不是翻译器。rust-anything 真正的定位是：一个让编程智能体来驱动的迁移工具箱，翻译那一步故意留给智能体或者你自己去做。

这篇文章拆解 rust-anything 的设计思路和几个关键特点。仓库我已经克隆到本地，下面引用的数字和决策都来自源码和文档。

一、第一个设计决策：不翻译代码

这一条是理解整个项目的关键。作者在设计决策文档（DECISIONS.md）里把第一条（D1）就写得很清楚：

A toolkit your agent drives, not a translator that calls a model itself.

翻译过来：这是给你的智能体使用的工具箱，而不是一个自己内置大模型的翻译器。

理由有三条：

  1. 不用付模型调用费，也不被某个模型厂商锁定。你用 Claude Code、Codex、Cursor、Gemini CLI 都行。
  2. 翻译这件事，智能体已经能做了。让工具再塞一个模型进去，是重复造轮子。
  3. 真正难的不是「生成 Rust」，而是「证明 Rust 是对的」。而这恰恰是智能体自己没法可靠完成的部分。

所以 rust-anything 把力气全花在「智能体可靠做不到的部分」上：

  • 时间花在哪了（profile）
  • 先迁哪块、按什么顺序迁（analyze）
  • 桥接层怎么生成，让上层调用 API 不变（bridge）
  • 原程序的真实行为到底是什么样（record）
  • 移植版本对不对（diff）
  • 到底快没快（bench）
  • 能不能安全上线（shadow）
  • 什么才算「做完了」（gate）

这是一个明确的取舍方向：很多 AI 编程工具想做的是「一句话把整个项目重写掉」，那其实根本不靠谱，也不现实，还可能引入很多幻觉，效率反而未必高。rust-anything 反过来选择少做一步——rust-anything 只负责把「原程序到底做了什么」这份权威基准记录下来，写 Rust 这一步交给智能体或人。

二、核心工作流：一条闭环流水线

rust-anything 把整个迁移过程固化成一条流水线：

官方文档里这段动图把整条流水线串了起来：profile 找出藏在循环里的热点函数 fuzzyScore，bridge --batch 生成 Rust 包，gate 用 2000/2000 条录制用例判定通过，最后的性能基准显示比 TS 快 20.7 倍。

profile ──> analyze ──> bridge ──> record ──> port.rs ──> diff ──> bench ──> shadow ──> gate

逐个说每步在干什么：

0. profile（测） 在语言自带的性能分析器（profiler）下跑一个真实负载（node --cpu-prof、Python 的 cProfile、Go 的 pprof、Java 的 JFR、Ruby 用 TracePoint），列出热点函数、调用者，以及哪个循环值得批量迁移。关键点是 profile 会标记那些已经被编译成机器码的代码（numba @njit、Cython、JAX），告诉用户迁这些几乎没提速。

1. analyze（规划） 把仓库切成「单元」（一个目录，或包根下的单个文件），按依赖关系排成「波次」（被依赖的先迁），给每个单元打两个分：就绪度（迁移有多安全）和优先级（安全且值不值得）。还会把 npm 包（Node.js 的包）映射到对应的 Rust 包（crate），映射不到的老实标 unknown，绝不瞎猜。

2. bridge（搭桥） bridge 为某个单元生成一个 Rust 包（crate）和桥接层，让上层调用方保持原有接口（API）不变。TS 用 napi-rs 或 wasm-bindgen，Python 用 PyO3，C 用 C ABI，Go/Ruby/Java 各自一套。bridge 生成的包分成两个文件：lib.rs（生成的绑定，允许 unsafe）和 port.rs（纯 Rust，强制 #![forbid(unsafe_code)]），其中 port.rs 才是用户要写代码的地方。

3. record（录制） record 是整条流水线的基准来源：没有 record 录下来的行为，后面的对拍就没有对照物。record 拿原程序在自动生成的边界用例上跑一遍，把返回结果和抛出的异常录成 cases.jsonl。这些用例专门踩「语义陷阱」：非 ASCII、emoji、-0、NaN、该填浮点的地方塞整数、字符串长度和大小写、有符号除法、溢出边界、浮点打印、map 和 sort 的顺序等等。相当于给原程序自动做了一份特征化测试套件（characterization suite）。

4. diff（回放对拍） 把录制的每一条用例拿去喂 Rust 实现，逐条对比。全对上才算过。

5. bench（测试定论） 把桥接开销也算进去，实测原实现与 Rust 的速度对比，最后给一个明确结论（verdict）：上线 / 这部分保留原语言 / 迁更大的单元 / （C 的话）优化移植。

6. shadow（影子模式） 一个即插即用的替换模块（drop-in），新旧两套同时跑，返回原实现的结果，只把 Rust 的不一致记进报告。用 RUST_ANYTHING_MODE=old|shadow|new 切换。上线时灰度用。

7. gate（闸门） 「做完了」的硬性定义：fmt、clippy 警告当错误、cargo test、unsafe 必须带 SAFETY 注释、不许有 unimplemented!、原程序每个会主动报错的路径都得有一条录制用例覆盖、原程序返回错误处不许 unwrap/expect/panic!，还有一个防臃肿规则——移植版代码行数超过原版的 3 倍就判不通过（超过通常意味着你在手写已有 Rust 包（crate）已经提供的东西，或者在逐个分支硬编码枚举）。

这条流水线的核心规则是：以原程序的实际行为为准。rust-anything 不改用户的代码去迎合结论，而是让结论去迎合录制的行为。对不上，改移植，不许改录制。

三、用 Rust 不一定更快

「承认 Rust 不一定更快」这一点在同类项目里相当罕见，rust-anything 直接把这一点写进了 FAQ：

Rust 一定更快吗？ 不一定，rust-anything 也会如实告诉你。

原因可能还很复杂。一个每条数据调用一次的小函数，在 Rust 里往往更慢，因为每次调用都要跨桥接层，而 V8、JVM、Go 跑这种函数是纳秒级的。项目里的 DECISIONS.md 有真实数字：colorsys 的移植版每次调用 11.7 微秒，CPython 原生才 0.5 微秒——JSON 序列化开销是实际工作量的 10 到 50 倍。

README 里那份 x18n core 案例研究是最好的例证：29 个函数全移植成功，7925 条录制用例全对，闸门全过——结果 bench 显示移植版从 JS 调用反而更慢，因为桥接成本超过了函数本身的工作量。作者把这个教训写进了 DECISIONS.md（X5）：速度不是正确性，但速度也可能用于决定是否该移植。

那 Rust 什么时候更快呢？答案是把数据留在 Rust 侧、尤其是用上多核优化。--batch 批量类就是按这条思路设计的：条目一次性过桥留在 Rust 里，之后每次调用在 Rust 内部对所有条目跑一遍、多核并行。实测对比（相同结果、4 核）：

语言 工作负载 单次调用移植 批量（batch）
TS x18n 搜索 5 万条 0.2-0.4x（更慢） 20x
Python slugify 2 万条 — 17x
Ruby shellescape 5 万条 — 11.8x
Go Slugify 5 万条 0.93x（更慢） 4x
Java slugify 5 万条 0.68x（更慢） 3x

下面这张官方对比动图，左边是原生的 TypeScript，右边是 rust-anything 的批量版本，都拿 x18n 的侧边栏搜索在 5 万个 key 上逐字符输入：TypeScript 累计花 143 毫秒，rust-anything 批量只花 6.9 毫秒，而每次按键给出的结果完全一致。

Go 和 Java 这种本身就跑得快的语言（是的你没看错，其实如果有JIT加持的话，Java也还是可以很快的），单次调用移植基本没啥优势，但一上批量了rust就反超了。rust-anything 甚至为了批量把 mimalloc 设成全局分配器——因为系统分配器会让多线程串行，实测慢到「比 Go 进程里单线程还慢」。

「先测再迁、用 bench 评分、接受 Rust 有时更慢」这一整套做法，和那种假设「换成 Rust 一定更快」就动手的重写工具，就是有本质区别了。

四、桥接层的具体处理

桥接是这类跨语言工具要面对的最麻烦的环节了，rust-anything 在这里的解决方案特别值得看，可谓踩坑实录了：

JSON 可能表达不了的 JS 值。 JSON 无法表达 undefined、NaN、Infinity、-0 和孤立代理项（lone surrogate）。rust-anything 用标记（{"$undefined": true}、{"$num": "NaN"}、{"$utf16": [...]}）在生成的加载器里翻译。这些标记每一个都对应真实的不一致 bug，比如 toWireRange 遇到 NaN、diffText 把 emoji 切一半（JS 的 indexOf 按 UTF-16 码元计数，一个 emoji 占两个位置——而 Rust 按 UTF-8 字节）。

不在热路径上传序列化后的 JSON 文本。 跨桥调用本来就该很快，如果每次调用都把参数和返回值先序列化成 JSON 字符串、过去再反序列化，这部分编解码开销会比函数本身的工作量还大（DECISIONS.md 里 colorsys 的例子：走 JSON 每次调用 11.7 微秒，CPython 原生才 0.5 微秒）。所以 rust-anything 对常用类型走原生转换：Python 在 Rust 侧直接转对象，Ruby 用 magnus 扩展，Java/Go 用类型化的 JNI/cgo 直接传数字、布尔、字符串，只有遇到这些原生通道表达不了的类型才退回 JSON。Java 更进一步：从 JNI 抛异常比从 Java 代码里抛慢 1.5 微秒，于是移植版把错误写进一个每线程的临时槽位，再由生成的 Java 代码负责把异常抛出。

浮点精度。 serde_json 默认解析器可能差 1 个最后有效位（ULP），Java 的 Double.toString 在 43 个用例里暴露了这个问题，于是所有生成的 Rust 包（crate）强制开 float_roundtrip。数值代码还可以用 --float-tolerance 1e-9 允许容差，但整数、文本、结构体仍必须精确一致。

这些细节说明作者在开发过程中是真地把六种语言端到端跑通过、被bug毒打过之后才总结出来的。

五、整应用迁移的分步实现

单个函数级别的证明只覆盖一个单元，一个完整应用还需要一份「整个程序对外行为一致」的证明。rust-anything 把整应用迁移拆成四步：先录一份黑盒基线，再把入口搬到 Rust，然后把单元一个个接过来，最后拆掉过渡层。

第一步，app record：录一份黑盒基线。 app record 把整个应用当成一个进程来看，不读源码。命令行工具项目里，app record 从项目文档里挑出 $ mytool ... 形式的命令行示例，再叠一批针对参数值的语义陷阱；HTTP 服务同理，从 curl 请求行抓样本，针对路径段和查询值加陷阱。每条用例把原实现跑两遍，把两次结果不一样的部分（时间戳、UUID）自动变成通配符。用例落盘用 trycmd 格式，可以手工编辑，之后 cargo test 时也能直接跑。

第二步，app front-door：把入口搬到 Rust。 前门（front door）是一个 Rust 可执行程序（HTTP 服务则是一个 axum 服务器），负责解析原应用的所有命令或路由，但每个入口一开始仍然原样调用原实现：命令行工具原样传参（命令行参数、标准输入、退出码），HTTP 服务通过代理转发。Rust 立刻拿到入口（main），而「新壳 + 老芯」跑起来和原来一模一样，app replay 从这一步起就能一直验到底。回退到原实现的次数在 app replay 报告里以回退率（fallback rate）显示。

第三步，app wire：把单元一个个接过来。 一个过了 gate（闸门）的单元用 app wire 挂到前门上，原本落到原实现的命令或路由改成调用这个 Rust 单元。每挂一次跑一次 app replay，回退率应该掉一截，直到所有单元都过闸门、回退率掉到 0。

第四步，app lift：拆掉过渡层。 app lift 只有在「app replay 全过 + 回退率降到 0 + 每个单元都过闸门」这三条同时满足时才允许运行，否则拒绝并列出阻塞项。app lift 剥掉所有桥接、绑定、影子和回退路径，把一堆单元的 Rust 包（crate）合并成一个干净的纯 Rust 可执行程序或库，原实现从此只作为参考留存。整个提升（lift）过程不动原代码。

六、给智能体写工作流，而不只是提供一个命令行工具

rust-anything 没有止步于一个命令行工具，rust-anything 把整条流程做成两份「智能体可读」的东西：

  1. 一个 MCP 服务器（rust-anything mcp），每一步都是一个 MCP 工具。
  2. 一个工作流技能（skills/rust-anything/SKILL.md 和 whole-app.md），是给智能体看的操作手册。

rust-anything setup 会自动把 MCP 服务器和技能注册到 rust-anything 检测到的每个智能体的配置文件里（~/.claude.json、~/.codex/config.toml、~/.cursor/mcp.json、~/.gemini/settings.json），而且只追加 rust-anything 自己的条目、保留用户其它配置、改之前先备份成 .rust-anything.bak。这是一个「改别人配置的命令绝不能弄丢别人配置」的细节考量（决策 S16）。

技能文档里给智能体定的「纪律」值得单独说，例如：

  • 规划完必须停下等用户批准再动手；
  • 整应用迁移要先「拷问用户」（grilling）：把迁移依赖的每个决策整理成一棵「设计树」，分轮提问，每个问题都带推荐答案，答案落成一条架构决策记录（ADR）写进 DECISIONS.md；
  • 一个跨会话的 MAP.md 记录每个单元状态，一个会话开工前先「认领」一个单元，收尾留一份 HANDOFF.md 交接给下一个会话——把长于一次会话的迁移工程做成可续接的。

上面这套「grilling / research / 跨会话交接」的做法，作者在 README 里注明是从 Matt Pocock 的技能 借鉴的。上面这套做法也是 rust-anything 最值得注意的信号之一：工具的能力边界正在从「给人用的命令」扩展到「给智能体用的带纪律的工作流」。

七、rust-anything 做不到的地方

rust-anything 靠的是「行为对拍」：把原程序跑一遍录下输入对应输出，再看 Rust 逐输入输出是否一致。这意味着验证范围永远超不出「录到的东西」。rust-anything 自己也很清楚这一层，在文档里专门开了一节列出录不到、因而验不了的地方：

  • 没录过的输入验不到。 rust-anything 能录的输入只有三类：自动生成的边界用例、针对各类陷阱的用例，以及你自己用 --inputs 补的真实样本。这三样之外的输入，rust-anything 不会知道。麻烦在于：线上真正让程序出故障的输入，往往是真实业务里才会出现的组合，很难被自动生成的用例碰上。要补这个缺口，得手动把线上样本、历史 bug 报告里的数据、原项目的测试夹具喂给 --inputs。

  • 正则表达式验不干净。 原语言（比如 JS、Java）的正则引擎和 Rust 的 regex 包（crate）不是同一套。regex 不支持环视和反向引用这类写法；就算某个正则在两边都能编译通过，遇到非 ASCII 文本时，像 \w、\d、忽略大小写这些规则的判定也可能不一样。结果就是：一条正则可能把你录的用例全跑对，却在土耳其语无点小写的 ı、零宽连字这种边缘字符上给出不同结果。rust-anything 会把这类陷阱字符塞进用例里多拦一道，但拦不干净，真要上生产的正则还得拿真实文本自己测。

  • 原程序两次运行本身就变的东西，只能放宽。 有些输出本来就不是固定的：内部用了哈希表，输出的行的顺序会随运行变化；带并发的代码，执行顺序也不固定。rust-anything 的做法是把每条用例先把原程序跑两遍，看看哪些部分两次不一样，再把不一致处当作模糊项处理（顺序不固定的就按「集合」而不是「顺序」去比）。问题是：这种顺序上的不确定性，恰恰是移植之后最容易真正跑歪的地方，而模糊化处理正好把这个隐患放过了。所以 rust-anything 会把这些放宽的部分逐个列出来，提醒人去人工确认。

  • 输出以外的东西一概不管。 对拍只比对程序「对外可见的结果」：标准输出、标准错误、退出码、写出来的文件、HTTP 响应。至于程序跑得花了多少时间、占了多少内存、高并发下的表现，以及网络请求、数据库写入、系统信号这类副作用，都不在比对之列，对拍层面看不到差异。

  • 换平台不保证一致。 录下来的行为只代表「跑录制的那台机器」。这在 C 代码上尤其明显：C 的数据类型多大、内存怎么摆、字节顺序（大端小端）如何，在不同机器和不同编译器上都可能不同。rust-anything 录的只是当前这台机器的结果，换一台机器未必成立。为此 analyze 会把那些跟硬件强相关的 C 代码（用了 volatile、位域、内联汇编，或结果依赖类型大小、字节顺序的）直接标成「保留在 C 里（keep in C）」，建议你别动。

rust-anything 也明确说了不能迁 APK/JAR/.exe（只面向源码，要有解析和行为可录），不能自动重构，UI/编辑器代码留在原语言。一个上线才三天的项目，文档里专门用一节列出自己做不到的事，而不是只宣传能力，这一点不常见。

八、胡乱总结一下

设计思路对 AI 时代的工具设计有参考价值。 rust-anything 没有做一个大而全、内置模型的自动重写器，而是把「智能体做不可靠的部分」（测量、排序、录制、对拍、定论、闸门）做成可编排的工具，把「智能体擅长的部分」（写 Rust）留出去，再用技能文档（对应项目里的 skill）把两者黏合成一条有纪律的流程。DECISIONS.md 里那句「checks 是智能体无法可靠完成的部分」，正是整个设计能立住的原因。

考虑把「正确性」和「速度」分开。 闸门（gate）管正确性，性能基准（bench）单独管速度并给结论（verdict）（决策 X5、S4）。很多移植工具会悄悄假设「Rust 一定更快」，rust-anything 用一堆实测数据反过来提醒用户：先测，别上线一个让调用方更慢的移植。

给整个智能体（agent）生态做基础设施。 MCP 服务器 + 多智能体配置注入 + 技能文档，这套组合的价值不在于 Rust 迁移本身，而在于 rust-anything 示范了一个命令行工具如何「一次开发、被所有编程智能体调用」。

JavaScript真是赶上了好时候啊。 rust-anything 对 TS/JS 支持最成熟，其它语言质量参差（Go/Java 的叶子函数迁移本身就打不过原生，全靠批量（batch）扳回来）；rust-anything 本质是行为对拍，行为之外的隐式契约（并发、副作用、别平台）测不到；而且迁移质量最终还是取决于写 port.rs 的那个智能体或人。整仓库约 3.8 万行 Rust，多种支持/预览语言各自的解析器、录制器、桥接、回放驱动都要端到端测，扩展到新语言的边际成本不低（作者 FAQ 里也承认每种语言要四件套）。

如果你想给手上的某个慢模块提速，或者琢磨一个中型项目的 Rust 迁移怎么落地，rust-anything 值得试试，至少用 profile 和 analyze 感受一下。而且 rust-anything 项目当中的那份 DECISIONS.md 本身就是一篇很好的「跨语言桥接会踩哪些坑」的实战笔记。
