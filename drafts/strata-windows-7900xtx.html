一张 RX 7900 XTX 的 Windows 小型主机跑 125B 大模型：Strata 实战记录

发布于 Mon 05 October 2026 | 23 分钟 | 标签 Strata 本地部署 RX 7900 XTX Windows Qwen3.8

一台 64GB 内存、单张 RX 7900 XTX 24G 的 Windows 小型主机，用 Strata 引擎把 1250 亿参数的 Qwen3.8-Flash-Next 跑出了长文本 38–51 tokens/s 的解码速度。下面把机器配置、每一步操作、实测成绩和遇到的问题完整记录下来，换机器也能照着复现。

GitHub 仓库 https://github.com/Niko1221/Strata 。

硬件与系统环境

项目 配置
整机 AMD 平台的小型主机
CPU AMD Ryzen 5 7640HS（6 核 12 线程，Phoenix，Zen3+）
内存 64GB DDR5-5600（单条 SO-DIMM，插槽式，非板载）；其中约 8GB 划给核显作共享显存，系统可用约 55.8GB
独显 AMD Radeon RX 7900 XTX，24GB 显存，gfx1100（RDNA3）
显卡连接 M.2 NVMe 转 OCuLink 转接（非原生 PCIe 插槽），链路带宽可能受限
核显 AMD Radeon 760M（gfx1103，会被虚报成 610M/gfx1036，见后文；共享约 8GB 内存）
NPU AMD XDNA 1（10 TOPS INT8，跑不了 LLM）
硬盘 WD_BLACK SN850X 4TB NVMe 固态硬盘（模型全部放在这块盘）
系统 Windows 11 Pro，build 26300
虚拟化 Hyper-V 层已激活（HypervisorPresent=True）

显卡驱动：

设备 驱动版本 日期
RX 7900 XTX 32.0.31041.1004 2026-08-17
Radeon 760M 32.0.31041.1004 2026-08-17
AMD Software（Adrenalin） 26.8.1 —

驱动就是普通 Windows Adrenalin 完整版（带 HIP runtime）。Strata 引擎包内部自带独立 ROCm，不依赖系统是否安装 ROCm，这是 Windows 路线最省事的一点。另外，注册表里 Smart App Control 已关闭（VerifiedAndReputablePolicyState = 0），这一状态对本项目很关键，后文会说明。

为什么用 Strata

Qwen3.8-Flash-Next 是 1250 亿参数的超大 MoE 模型，若按常规做法把全部参数加载进显存，需要数百 GB 显存，普通机器根本放不下。

Strata 的思路不同：MoE 每层 512 个专家只激活 top-10，于是把专家权重常驻系统内存（必要时下探到 SSD），只让高频命中的专家进显存缓存，激活时按需搬运，再叠加 MTP 投机解码。这样 24GB 显存加 64GB 内存的普通机器就能喂饱 125B。项目文档记录了 RX 7900 XTX（gfx1100）在 Linux 下的量级：解码约 55–88 tokens/s、预填充最高约 966 tokens/s。

此前 Strata 的三层调度（显存 / 内存 / SSD）主要在 Linux 上使用。本次实测表明，官方 Windows HIP 预编译包已经可用，速度与 Linux 差距不大。

从零开始的完整操作

下面示例以 C:\Strata 为项目目录、C:\Strata-data 为数据目录，实际可按需替换。文中 tools\、serve\、data\ 等目录，以及其中的脚本（iq_pack.py、mtp_fetch.py、mtp_pack.py、mtp_rt.py 等）都是克隆下来的项目自带内容，无需另行下载；仅用于批量下载模型、跑分、一键启动的少数脚本属于自行准备。

第 0 步：装好基础工具

动手前先把基础工具装好：Git（克隆与版本管理）、Python 3.10 以上（自带 venv，用于打包、服务器与跑分）。Windows 上到各自官网下载安装包即可，安装时记得勾选加入 PATH。若不清楚怎么装，或中途报错，可以让本地的 AI 编程助手（例如 opencode）代劳，直接说明要安装 Git 与 Python 并加入 PATH 即可。

Windows 11 自带 winget，也可以直接用命令行安装（供参考）：

winget install --id Git.Git -e
winget install --id Python.Python.3.13 -e
winget install --id 7zip.7zip -e

装完后新开一个终端，能分别打印版本号即成功：

git --version
python --version

其余步骤用到的工具都在项目里，不需要额外安装。

第 1 步：克隆项目

拉取完整历史，不要浅克隆：

cd /d C:\
git clone https://github.com/Niko1221/Strata.git
cd Strata

如果国际网络访问不畅，可改用加速镜像：

git clone https://ghfast.top/https://github.com/Niko1221/Strata.git
cd Strata && git remote set-url origin https://github.com/Niko1221/Strata.git

第 2 步：获取引擎（Windows 最省事的路线）

仓库文档曾写 HIP 后端“仅 Linux”，这条信息已经过时。官方 Releases 从 0.1.33 起直接提供 Windows HIP 预编译包：

https://github.com/Niko1221/Strata/releases/latest
  strata-windows-x64-hip.zip   ← 约 571MB，内含 ROCm 运行时与 gfx1100/1101/1200/1201/1030 内核

解压到仓库的 engine\ 目录即可，strata.exe、strata-device.exe 与 rocm\bin\ 都在其中。不需要 WSL，不需要系统级 ROCm，也不需要自行编译。

如果想自行编译（Linux 或本地构建），用 setup 脚本自动装 ROCm（TheRock wheels，无需 sudo）并 CMake 编译：

cmake -S . -B build-hip -DCMAKE_BUILD_TYPE=Release `
  -DSTRATA_ENABLE_HIP=ON -DSTRATA_ENABLE_CUDA=OFF `
  -DSTRATA_HIP_ARCH=gfx1100 -DSTRATA_NATIVE_EXPERTS=ON -DSTRATA_PREFILL_MMQ=ON

第 3 步：Python 环境

引擎本体是 C++，但打包工具、服务器、bench 都需要 Python：

cd C:\Strata
python -m venv .venv
.venv\Scripts\python.exe -m pip install -i https://mirrors.aliyun.com/pypi/simple/ numpy regex jinja2

部分镜像源对 pip 的 /simple/ 会返回 403（curl 却是 200，UA 被拦），换阿里云源即可。

第 4 步：下载模型（ModelScope 直连）

社区里部分量化是 gated 仓库，直连返回 401，需要账号同意条款，不折腾就用官方支持的主线量化 ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF，该量化在 ModelScope 有逐字节一致的镜像，国内直连稳定。

每个量化档两片 GGUF，其中第二片（28.8GB 的 PLE 查找表）多档共用，只下这一份再硬链接即可。四档去重后总计约 208GB；只跑 IQ3_XXS 约 43.8 + 26.8 ≈ 70.6GB。

下载接口（支持 Range）：

https://modelscope.cn/api/v1/models/{repo}/repo?Revision=master&FilePath={path}

一个稳妥的下载脚本（自备）会做几件事：多连接分块加位图边下边存，中断不丢进度；下完核对 SHA-256。

IQ3_XXS 最终两个文件：

文件 字节数 内容
Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS-00001-of-00002.gguf 47,039,860,096 专家权重 + dense
Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS-00002-of-00002.gguf 28,800,138,432 PLE n-gram 查找表

第 5 步：GGUF 转 Strata pack

.venv\Scripts\python.exe tools\iq_pack.py --gguf C:\Strata-data\models\IQ3_XXS\Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS-00001-of-00002.gguf --out C:\Strata-data\packs\iq3_xxs

GSQ-RCO 本身按 Strata 的几何量化，不需要 --compat-bf16（那个只有普通量化才要）。产出 dense.bin（1.54GB）、index.txt、native_experts.txt、tokenizer\。

第 6 步：MTP 投机解码 runtime

MTP draft head 在 360GB 的 BF16 原始 checkpoint 里，但 safetensors 有 JSON 头，用 HTTP Range 只拉需要的 31 个 MTP tensor，取到的数据量很小：

.venv\Scripts\python.exe tools\mtp_fetch.py fetch --out C:\Strata-data\mtp
.venv\Scripts\python.exe tools\mtp_pack.py --src C:\Strata-data\mtp --experts q2_0 --out C:\Strata-data\mtp\mtp-q2_0.gguf
.venv\Scripts\python.exe tools\mtp_rt.py --gguf C:\Strata-data\mtp\mtp-q2_0.gguf --out C:\Strata-data\mtp\rt
copy data\draft_vocab.bin C:\Strata-data\mtp\rt\draft_vocab.bin

若 huggingface.co 直连不通，把 tools\mtp_fetch.py 里的仓库地址前缀换成镜像站点即可。

第 7 步：启动配置

strata-iq3_xxs.json 关键字段：

{
  "exe": "C:\\Strata\\engine\\strata.exe",
  "args": ["--pack", "C:\\Strata-data\\packs\\iq3_xxs",
           "--native", "C:\\Strata-data\\models\\IQ3_XXS\\Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS-00001-of-00002.gguf",
           "--ple-gguf", "C:\\Strata-data\\models\\IQ3_XXS\\Qwen3.8-Flash-Next-GSQ-RCO-IQ3_XXS-00002-of-00002.gguf",
           "--expert-profile", "C:\\Strata\\data\\expert-profile.bin",
           "--expert-cache", "auto", "--prefill", "auto",
           "--spec", "4", "--spec-min-p", "0.5",
           "--mtp", "C:\\Strata-data\\mtp\\rt",
           "--max-context", "131072", "--kv", "int8"],
  "model_name": "qwen3.8-flash-next-iq3_xxs",
  "port": 8080, "backend": "hip", "gpu": 1
}

进阶参数（--mmap-experts、--resident-cpu-experts、--kv-resident 32768、--pool-workers 15 等）可以进一步榨性能；v0.1.37 的默认 resident 行为已接近，先跑基线再调。

第 8 步：运行

.venv\Scripts\python.exe -m serve.server --engine strata --config strata-iq3_xxs.json --port 8080

Web 聊天页 http://127.0.0.1:8080/，API http://127.0.0.1:8080/v1/chat/completions（OpenAI 兼容、无鉴权，模型名 qwen3.8-flash-next-iq3_xxs）。

实测成绩

重启后的干净环境启动日志：

[strata] loading the experts into RAM (about 47 GB) and locking part of them for the GPU.
[strata] experts loaded: 39.97 GiB at 3.10 GiB/s (26 s so far)
[strata] filling the GPU's expert cache (9519 experts, 15.43 GiB of VRAM) ...
ready: http://127.0.0.1:8080/v1  (context 131072 tokens)

从冷启动到可服务约 35 秒（顺序读被吃满 3.1GiB/s，这是 NVMe 固态硬盘的价值）。显存驻留约 15.4GiB 加 KV，内存常驻 39.97GiB。

五类任务的解码速度（两轮冷启动均值，客户端与引擎自报两个口径并列）：

解读：

  • 解码：生成越长越接近稳态，math 满窗引擎口径 50.8 tokens/s；短答偏低，是 MTP 草稿接受率没起来。
  • 预填充：长 prompt（3736 token）达 441 tokens/s；短任务 40–55 tokens/s，prompt 越长 batching 越充分。
  • 可复现：两轮冷启动偏差在 ±5% 内。
  • 独显经 M.2 NVMe 转 OCuLink 转接（并非原生 PCIe 插槽），链路带宽有限，可能是部分场景速度未达预期的原因之一；即便如此，长生成仍能到 50 tokens/s 量级。

正确性抽查：fizzbuzz 一次写对；概率题 15/28 ≈ 53.57%（正确）；自述正确。

长期运行实测（6 小时连续）

前面两轮冷启动只证明了“跑得起来”，真正让人心里没底的是长时间挂着会不会衰减。于是把服务连续跑了 6 小时（360 分钟），期间每约 15 分钟打一次探针，在开机、第 2 小时、第 4 小时各跑一轮 7 项工具调用自检，累计记录 7799 次实测请求。四条曲线（预填充 / 长生成 decode / 短探针 decode / 缓存命中）放在同一张图里，都很平：

  • 预填充：探针均值 329 tokens/s，线性趋势 +0.9 t/s/小时，没有随时间变慢。
  • 长生成 decode：把 7799 次请求按累计耗时归桶后，真实生成 decode 均值 52 tokens/s，全程稳在 50 上下。
  • 短探针 decode：均值 5.2 tokens/s，基本持平。它固定只生成十几二十个 token，只用来判断“平不平”，不代表真实解码速度。
  • 专家缓存命中：均值 82%，趋势 +0.8%/小时，不降反微升，缓存没有越跑越乱。

为什么短探针只有 5 t/s、长生成却有 52 t/s？

这两个数差了十倍，很容易让人以为机器忽快忽慢，其实差在“测量口径”和“是否进入稳态”：

  • 短探针慢，是被固定开销拖的。它只生成十几个 token，而一次请求里有一大块耗时跟生成长度无关——prompt 处理、KV 建立、专家调度、HIP kernel 启动与同步、MTP 草稿头热身。这些开销摊到十几个 token 上，t/s 自然低。它衡量的是“最小请求的端到端响应”，不是解码能力。
  • 长生成快，是因为进了稳态。MTP 投机解码的草稿接受率升到约 70%，一次前向就能出好几个 token；命中的专家已经躺在 24GB 显存缓存里（命中率约 80%），绝大多数 token 不需要再从内存/SSD 搬权重。这时 GPU 大部分时间在算、不在等数据，速度自然回到 50 t/s 上下。
  • 跟 OCuLink 链路的关系：这张 7900 XTX 不是原生 PCIe ×16 插槽直连，而是走 M.2 转 OCuLink 外接，链路会有信号损失、带宽打折。它主要拖累预填充：预填充要一次性把大量专家权重喂进显存，链路一慢就跟着慢，本机长 prompt 预填充只有约 330–441 t/s，明显低于 Linux 参考的约 966 t/s。稳态 decode 主要吃已经缓存在显存里的专家，搬运量小，受链路影响小，所以反而更接近 GPU 的算力上限。

7799 次请求的 decode 分布：中位 52、均值 52、最大 89 tokens/s，主体集中在 40–65。短答（reason 类）因为草稿接受率还没起来、固定开销被摊薄，会落到 30 多。MTP 投机解码草稿总接受率 70.7%。

缓存命中率分布：中位 81%、均值 79.9%、最高 97%，多数请求在 75% 以上。命中率越高，要从内存/SSD 搬运的专家越少，decode 越快。

工具调用自检用矩阵看最直观：冷启动首轮 7 项只过 4 项（T1 单工具、T4 强制选择、T5 工具回环未通过，是显存/专家缓存还没热），此后每轮都是 7/7，连续 3 轮无回退。

内存水位：空载可用 44.4GiB；加载后 Strata 工作集约 40GiB、提交量约 56GiB，系统只剩 3.1GiB，跑完 6 小时仍是 2.8GiB，没有持续泄漏——压线但不恶化。

这台机器连续跑 6 小时，吞吐、缓存命中、内存、工具调用都没有衰减迹象，可以放心当本地服务长期挂着。

需要注意的问题

  1. Smart App Control 会拦新二进制。若系统开着 SAC（VerifiedAndReputablePolicyState=1），任何新建的未签名 exe 会直接以 0xC0E90002 退出、零输出，解压出来的 strata.exe 根本无法启动。开工前先到 Windows 安全中心关闭 SAC。
  2. “Windows 不支持 HIP”是过时信息。仓库某文档仍写 Windows HIP 不在范围内，但 GitHub Releases 实际在发 strata-windows-x64-hip.zip，只信文档会白装一个 WSL。
  3. 部分社区量化是 gated 仓库，直连与镜像都返回 401，需要账号同意条款；不折腾就用官方主线的 GSQ-RCO 量化。
  4. hipBLASLt 校准表版本严格匹配。引擎 BUILD.json 声明 hipblaslt_version: 100500，仓库表只到 100200，会被全部拒绝加载，日志不报错但 dense 矩阵乘悄悄降级。预填充想快就得自行校准。
  5. 显存不能与人分享。同一套配置若被其他程序占用显存，专家缓存会被挤爆、命中率下降，解码速度骤降。跑 Strata 前先停掉其余占用显存的服务，重启最干净。
  6. 内存压线。47GB 专家进内存后，64GB 的机器（核显占用约 8GB，系统可用约 55.8GB）只剩 1.4–1.8GiB，已经很紧张了，所以确实是建议 64GB 起步。
  7. 开发环境杂项：这台 Windows 的 Bash 工具会重写路径、PowerShell 有沙箱限制，长路径命令一律落到 Python 脚本执行；pip 装包用阿里云源。
