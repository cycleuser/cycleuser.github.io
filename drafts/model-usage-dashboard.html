用Harness的思路用OpenCode：让智能体给自己做了个用量仪表盘

发布于 Fri 23 October 2026 | 9 分钟 | 标签 OpenCode 模型计费 token 用量监控 智能体 DeepSeek Ollama MiniMax

我手上的模型有点多了。

DeepSeek 是按量扣余额，充多少用多少；Ollama Cloud 是订阅加窗口额度，五小时一个会话窗口，一周一个周窗口；MiniMax 是套餐，五小时窗口加周窗口；腾讯那边还有 TokenHub 和 Coding Plan；再加上 Halogen、Strata 这些自建网关，Hugging Face 上一堆按量模型，OpenCode 自带的免费模型。

这些模型分散在四五个平台，每个平台一套账单口径。以前我想知道“这个月到底花了多少”，得一个个登录后台看。想知道“Ollama 这周还剩多少”，也得打开网页。平时在 OpenCode 里用的时候，界面上能看见的只有速度，花了多少、额度还剩多少，一概不知道。 我要一个能随时查的账本：每个模型用了多少、最近一个计费周期是从哪天到哪天、已经用了多少、还剩多少，全部要能看见。

这篇文章记一下这次是怎么做的，中间踩了哪些坑，最后出来是什么效果。

我的原话大概是这样：

当前设备目前已经配置好的这些个模型有很多种。有的模型是按量付费，得知道用的超没超、达到多少量了，要想办法随时能查。有的呢，是按量计费，它不限制，但是用得越多越贵，所以想办法来一个动态监控当前所有模型使用的情况。每次激活的模型都能随时看，目前最近计费周期时间内是多久到多久，然后已经用了多少、还剩多少。所有信息全要显示，不光是只有速度。

这段话里其实藏了三个不同的需求，后来也对应了三层实现：

  1. 按量付费的：DeepSeek 这种，没有固定周期，关键是余额和消耗速度。
  2. 有套餐额度的：Ollama、MiniMax 这种，关键是窗口什么时候重置、还剩百分之多少。
  3. 用得越多越贵的：需要按模型拆开看，哪个模型在烧钱，单价是多少，本月预测会到多少。

还有一句容易被忽略的：“每次激活的模型都能随时看”。意思是不能只给一个总账，得跟着当前会话的模型走。你在 OpenCode 里切到哪个模型，状态行就得显示哪个模型的账。

我把这个活整个交给了智能体。我负责说清楚要什么、在关键的地方判断它做得对不对；它负责查接口、读数据库、写代码、做界面、自己测试。

OpenCode 的数据库在 ~/.local/share/opencode/opencode.db，里面有一张 message 表，还有一张 session_message 表。一开始它只读了 message，面板上显示“最近使用是 13.6 天前”，今天的用量一条都没有。我当时就觉得不对：我明明正在用，怎么可能 13 天没动。

后来翻表结构才发现，新版 OpenCode 把会话消息写进了 session_message，message 是旧版的存储。两张表的 id 还有大量重叠，直接相加会重复计费。它最后做的是按 id 合并，V2 的记录优先，旧版里独有的再补进来。合并之后本地一共三万多条助手消息，今天的用量才出来。

这件事说明一个很朴素的道理：先搞清楚数据在哪，再谈统计口径。如果一开始就闷头写聚合，后面全是错的。

那么，各家厂商到底愿不愿意把额度给你看呢？

OpenCode 挨个试了接口：

  • DeepSeek 有 GET /user/balance，直接返回人民币余额，还拆成充值余额和赠送余额。
  • Ollama Cloud 有 GET /api/balance，返回会话窗口、周窗口的剩余百分比和重置时间；还有 /api/usage?range=7d&group_by=model，能给官方七天按模型的请求数。
  • MiniMax 有 GET /v1/token_plan/remains，返回五小时窗口和周窗口的剩余百分比。
  • Hugging Face 有 /api/whoami-v2，能拿到计费模式和账期结束时间，但拿不到额度数字。
  • 腾讯 TokenHub / Coding Plan 的套餐详情在腾讯云控制面 API 里，要 SecretId、SecretKey 和 TeamId，光有推理用的 API Key 不够。
  • Halogen、Strata 这些自建网关，接口里只有模型列表，没有账单。

这一步很关键，不能假设所有厂商都能查到额度，而是把能查的、不能查的分开。能查的走官方接口，不能查的明确标成“本地估算”。后面面板上每个 provider 都有这个标记，我觉得这个诚实比数字好看更重要。

接下来就是看看价格怎么计算，OpenCode 自己记录了每条消息的 cost，这个数可以直接用。但有些模型没有单价，比如旧版的 deepseek-chat、deepseek-reasoner，还有自建网关。用 models.dev 的目录补单价，再按输入、输出、缓存读分别乘 token 数。涉及到汇率就每天取一次，取不到就用 7.1 兜底。

于是账就有了三个层次：底层是每条请求的原始记录，中间是按周期聚合，最上面才是厂商的官方余额和额度。三者对得上最好，对不上就分开说，不硬凑。

我原本以为“最近计费周期”就是一个自然月。实际上不是：

  • Ollama 的额度是五小时会话窗口加七天周窗口，重置时间由官方接口给。
  • MiniMax 是五小时窗口加周窗口，时间也由接口给。
  • DeepSeek 是余额制，根本没有固定周期，充进去用到完为止。
  • Hugging Face 是预付费，账期结束时间从账户接口拿。
  • 自建网关这些，没有公开周期，只能按自然月做预算视图。

所以最后的规则是：官方接口给了窗口就用官方的，没给就用配置里的周期，再没有就默认自然月。自然月只用于“这个月大概花了多少”的预算视角，不会冒充厂商账单。

面板上每个 provider 的周期都写清楚了起止时间。比如 DeepSeek 会写“自然月 10-01 00:00 → 11-01 00:00”，后面再补一句“余额制：无固定周期，余额耗尽为止”。第一次看可能觉得啰嗦，但这是把两种完全不同的计费方式放在一张表里必须付的代价。

这样一来，同样是“还剩多少”，不同厂商给的东西那就可能很不一样：

类型 数据来源 面板上的说法
余额制 DeepSeek 官方余额 余额 ¥590.12，按当前速度约可用 75 天
窗口百分比 Ollama、MiniMax 官方接口 周窗口剩 33%，5 小时窗口剩 80%
手工套餐额度 配置文件里填的额度 总额度减去本地估算花费
没有额度 自建网关、免费模型 只显示 tokens 和估算花费

同一个面板上，DeepSeek 的余额是官方接口来的，Ollama 的 33% 也是官方接口来的，但“本月花了 ¥384”是本地按 token 乘单价算的。

这三个数放在一起，如果不标清楚，会以为 ¥384 是账单，其实不是。

所以每个 provider 卡片右上角都有一个标记：官方额度 或者 本地估算。官方接口失败的时候会显示错误，不会悄悄退回估算值。Ollama 官方七天用量包含非 OpenCode 客户端的调用，本机记录只包含 OpenCode 的调用，两个数对不上是正常的，面板上会把两个都列出来。

状态行跟着当前会话的模型走。你在 OpenCode 里切模型，它下一帧就换成新模型的账。下面是同一套数据，不用再开一个终端。

从我开始提要求，到状态行在 OpenCode 里跑起来，前后两个多小时。代码基本是它写的，我没怎么动手，主要是在旁边看数字、挑毛病、定方向。

如果让我自己写，我大概会先写一个读数据库的脚本，把今天的 token 一加，然后发现 DeepSeek 的余额对不上，再去查接口；查到 Ollama 发现要处理两种窗口；再查到 MiniMax 发现 POST 不通；最后在终端宽度和插件 API 上耗掉半天。这些活单拎出来都不难，但串在一起很磨人。

智能体把这一串都走了一遍，而且每一步都留了退路：接口拿不到就标“本地估算”，表结构变了就两套表合并，插件命令不执行就把入口删掉。它没有为了让界面好看而编数字，这一点我比较满意。

现在我的用法很简单：平时看输入框上方的两行状态，想知道细节就敲 mm，想盯着看就 mm watch -i 5。DeepSeek 的余额、Ollama 的周窗口、MiniMax 的五小时窗口，都在眼前。

这套东西现在只在我这台机器上跑，没打算做成通用产品。真要给别人用，光是不同厂商的额度接口和配置就够再折腾一轮。

大家要是有类似需求，其实完全可以考虑参考类似思路，让智能体工具自己对自己进行改进增强。
